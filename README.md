# Taiwan Science Events — GitHub Pages edition

Static GitHub Pages site plus a scheduled GitHub Actions updater.

## Repository layout

- `dist/` — the complete static site published to GitHub Pages.
- `dist/data/events.json` — initial seed data in Git; latest data is restored and generated during Actions runs.
- `update_events.py` — event collector.
- `reports/latest.json` — updater diagnostic report generated by Actions.
- `.github/workflows/pages.yml` — daily update + Pages deployment workflow.
- `.github/scripts/find-event-data.cjs` — selects the latest successful data artifact.

## First deployment

1. Create a GitHub repository and upload/push the contents of this folder to the `main` branch.
2. Open **Settings → Pages** and set **Source** to **GitHub Actions**.
3. Open **Actions → Update events and deploy Pages → Run workflow** once. This first manual run fetches the current data and deploys the site.
4. Later runs happen automatically every day at **06:15 Asia/Taipei**.

The project page URL will normally be:

`https://YOUR-USERNAME.github.io/YOUR-REPOSITORY/`

All site resources use relative URLs, so the site works under a GitHub Project Pages subpath without editing the repository name into the source files.

## Daily data storage and deployment

Daily updates do not commit or push generated files. Every run first restores
the newest unexpired `event-data` artifact from a successful run of `pages.yml`
on `main` in this repository. Scheduled and manual runs then refresh the data;
code pushes reuse the restored data without crawling. This preserves historical
events and failed-source fallback records, and avoids reverting to the seed JSON
when deploying a code change.

After JSON validation, the workflow saves `events.json` as `event-data` with
90-day retention and deploys `dist/` through the Pages artifact. Repository or
organization retention limits may shorten that period. Only snapshots from
completed successful runs are used on subsequent runs. Updates that exit nonzero leave the
previous Pages deployment and successful snapshot available; their diagnostic
report is uploaded separately as `updater-diagnostics` with 30-day retention.

The daily workflow uses `--allow-partial`: when a source fails but another source
has usable pages, healthy sources are published and failed sources retain older
records with `stale` markers and an `error` status. Actions logs show a warning;
the report includes `failed_sources`, `degraded`, and `exit_code`. Such a run can
complete successfully and its merged data becomes the next snapshot. If all
sources fail, or preview generation fails, the updater still exits 2 and stops
deployment. The default local CLI remains strict unless this flag is supplied.

An HTTP 401/403 from `robots.txt` stops that source immediately; the collector
does not treat access denial as an empty robots file or fetch its event pages.
This may require the institution to allow GitHub-hosted runners; retaining older
data does not restore live access to the blocked source.

For the first run, or when all usable snapshots have expired or been deleted,
the workflow logs a warning and uses the Git-tracked seed JSON. In that case,
past events no longer present on source websites may be unavailable. API,
authentication and artifact-download failures stop deployment rather than
silently substituting older seed data. Keep scheduled runs enabled to renew the
saved snapshots. Artifacts are rolling storage, not a permanent archive.

The workflow requires `contents: read`, `actions: read`, `pages: write`, and
`id-token: write`; no repository write permission or extra secret is needed.
When changing application code, do not include locally generated data changes
unless intentionally updating the initial seed. Generated reports and offline
previews are ignored by Git.

## ASIAA mode

The workflow runs the updater with `--asiaa-access public-html`, matching the previously tested public-HTML mode. The updater still records the site's robots directives in its diagnostic report; HTTP success is not treated as authorization.

## Local update

```bash
python -m pip install -r requirements.txt
python update_events.py --asiaa-access public-html
```

For local viewing, serve `dist/` over HTTP rather than opening `index.html` directly, for example:

```bash
python -m http.server 8000 -d dist
```

Then open `http://localhost:8000/`.

The updater also generates `preview.html` with embedded data and assets for
offline viewing. The website and preview share the same data loader.

## TLS compatibility and checks

Python 3.13+ enables strict X.509 extension checks. The TWCA chains currently
served by `www.math.sinica.edu.tw`, `www.phys.ntu.edu.tw`, `phys.ntu.edu.tw`, and
`www.iams.sinica.edu.tw` can fail with `Missing Subject Key Identifier`.
The collector relaxes only `VERIFY_X509_STRICT` for these exact HTTPS hosts on
port 443. Trusted CA signatures, hostname and expiration checks remain enabled;
other hosts and redirect destinations use the normal defaults. This applies to
both `robots.txt` and event pages, without changing robots enforcement.

Run the regression checks with `python -m unittest discover -s tests -v`.
Run artifact-selection checks with `node --test tests/test_event_data.cjs`.
